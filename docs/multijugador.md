## Summary
Online two-player game, each player on their own device, in js/red.js: the start menu offers '1 JUGADOR', 'CREAR PARTIDA' and 'UNIRSE'. Creating a game opens a room with a 4-letter code and shows it with a QR of the game link (?sala=CODE); the other player scans the QR or types the code under 'UNIRSE'. The two browsers connect directly (WebRTC with PeerJS, vendored in js/lib; PeerJS's free server only introduces them). The host (J1) runs the whole game and sends a snapshot 30 times per second; the guest (J2) draws it interpolated 80 ms behind and moves its own ship at once, sending its position and the shots it asks for. Cooperative: each player has 3 ships, their own points (J1 and J2 in their ship's colour) and their own power-up; the game ends when neither has ships. If a player stops being heard the game pauses for up to 30 seconds; then the host carries on alone and the guest returns to the menu. Pending the owner's validation.

- 2026-10-04 12:09 · Preferred form: online, each player on their own device.
- 2026-10-05 10:07 · Two players at once in the same game, each with their own device.
- 2026-10-05 10:07 · Communication feasibility: yes, it is possible. With a direct connection between browsers (WebRTC) a message takes about 5 to 20 ms on the same network and about 30 to 100 ms over the internet. One device acts as host and decides the enemies, the bombs and the hits; each device sends only its ship's position and shots 30 to 60 times per second, and the other player's ship is drawn smoothed. Galaxian is slow compared with that delay, so the game flows. Risk: on some networks (especially mobile data) the direct connection fails and a relay server (TURN) is needed, which adds some delay and may have a cost. Recommendation: check it with a small prototype before deciding.
- 2026-10-12 15:06 · Technology options weighed for the least lag (the browser cannot open raw network sockets, so the choices are WebRTC or WebSocket):
  - WebRTC data channel, peer to peer, unreliable and unordered (like UDP: a lost message is not resent, the next one replaces it): the fastest, 5 to 20 ms on the same Wi-Fi and 30 to 100 ms over the internet. It only needs a server to introduce the two devices (signaling) and a public STUN server to find each one's address; neither carries game traffic. Recommended.
  - WebSocket relay (for example Cloudflare Durable Objects or PartyKit): every message goes through a server over TCP, so it adds a second leg and a lost packet holds back the following ones; about 40 to 150 ms. Works on every network, but needs a hosted service.
  - Real-time database (Firebase, Supabase): built for app data, not for 30 to 60 updates per second; 100 ms or more and free-plan limits. Discarded for gameplay; possible only for signaling.
  - Local network only: still WebRTC (a browser cannot host a server), so it does not save anything; same Wi-Fi simply gives the lowest numbers.
  - Signaling choices: PeerJS public broker (free, a script from a CDN, no account; no service guarantee, replaceable later by our own free broker); manual exchange of the connection data by QR in both directions (no service at all, but two scans per game); Trystero over public relays (no account, less predictable). Recommended PeerJS.
  - Fallback relay (TURN) for networks where the direct link fails (some mobile data and corporate networks): free plans exist (for example Cloudflare, Metered); it adds a few tens of ms. Add it only if the prototype shows it is needed.
- 2026-10-12 15:06 · Lag handling proposed: the host runs the game (formation, attacks, bombs, hits, power-ups) and sends its state 30 times per second; each device moves its own ship locally at once (no lag on your own controls) and sends its position and shots; the other ship and the enemies are drawn interpolated. The guest's hits are decided by the host, a few hundredths of a second later.
- 2026-10-12 15:06 · Pairing proposed: "create game" on the host shows a 4-letter code and a QR with the link https://dinamicatech.github.io/KillerFlies/?sala=CODE; the guest scans the QR with the camera (opens the game straight into the room) or types the code under "join game". The code is the room name in the introduction service. Works mobile with mobile, computer with mobile, on the same Wi-Fi or over the internet.
- 2026-10-12 15:06 · [replaced by 2026-10-13 07:12] Architecture impact if executed: the game would load one external library (PeerJS) from a CDN and depend on free external services for the introduction (and TURN if needed); there is still no server of our own and it stays on GitHub Pages. Recommended next step: a small prototype (two ships moving between two devices, showing the measured lag) before deciding.
- 2026-10-13 06:53 · How the guest sees enemies, bombs and the rest (proposed): the host sends a full snapshot of the game 20 to 30 times per second (every 33 to 50 ms; the 5 to 20 ms of the network is travel time, not the sending interval) with every enemy's position and state, bombs, shots, capsule, points, lives and wave; in binary it is under 500 bytes, about 15 KB/s. The guest keeps drawing at 60 frames per second interpolating between the last two snapshots, so it sees the game about 50 to 80 ms behind the host but without jumps; its own ship moves at once. A lost packet does not matter because the next snapshot replaces it; explosions and sounds are triggered on the guest when it sees the change between two snapshots. Discarded: both devices simulating the game and exchanging only events (less data, but any small drift shows each player a different game). The prototype should confirm these figures.

- 2026-10-13 07:12 · Menu: under 'START GAME' the options '1 JUGADOR' (selected by default), 'CREAR PARTIDA' and 'UNIRSE'. Up and down arrows change the option and any other key chooses it; on the touch screen, tapping an option chooses it and tapping elsewhere chooses the selected one. So any key or tap still starts a one-player game as before.
- 2026-10-13 07:12 · Room: 'CREAR PARTIDA' makes this device the host (J1) and shows 'SALA', the 4-letter code (letters without I or O) and a QR of the game address with ?sala=CODE; any key or tapping 'CANCELAR' goes back to the menu. 'UNIRSE' asks for the code in a browser text box; opening the QR link joins straight away. If the room does not answer within 10 seconds (or PeerJS says it does not exist) it shows 'SALA NO ENCONTRADA'.
- 2026-10-13 07:12 · Connection: PeerJS 1.5.5 and qrcode-generator 2.0.4 are copied into js/lib (MIT licences) instead of loading them from a CDN, so nothing depends on a CDN and they can be tested offline. The room name in PeerJS's free server is killerflies-CODE; that server only introduces the devices, and PeerJS's own public STUN and TURN servers are used when the direct link needs them. One data channel, unordered, with JSON messages. For local tests, ?servidor=host:port uses another PeerJS server.
- 2026-10-13 07:12 · Synchronisation: the host runs formation, attacks, bombs, hits, power-ups and the game cycle, and sends 30 times per second a snapshot (about 250 bytes) with the game state, wave, formation position, each alien ship (dead, in formation or out), diving ships, bombs, capsules, bomb waves, and each player ship (position, state, shield, power-up, spare ships, points, shots). Bombs, shots, capsules and waves carry an id so they can be matched between snapshots. The guest draws 80 ms behind the latest snapshot, interpolating positions between the two around that moment; explosions, sounds and the shot flash come from the changes between snapshots, so a lost message does not matter. The guest moves its own ship locally and sends 30 times per second its position and a count of the shots it asks for; the host places J2 there (interpolated) and fires for it.
- 2026-10-13 07:12 · Disconnection: with no message from the other player for 2 seconds (or the connection closed) during a game, both pause with 'ESPERANDO A J1/J2' and a countdown; the guest keeps calling the room every 2 seconds and the game resumes as soon as messages arrive again. After 30 seconds the host carries on alone (J2 is out) and the guest shows 'CONEXION PERDIDA' and returns to the menu. After 'GAME OVER' there is nothing to wait for: a key or tap on either device closes the connection and returns to the menu.
- 2026-10-13 07:12 · Tested in two browsers with a local PeerJS server: one-player game unchanged, room with QR, joining by link and by code, both devices see the same game, J2 moves and scores, pause and resume after a cut, host alone after 30 seconds, 'SALA NO ENCONTRADA' and 'GAME OVER' back to the menu. Not tested on real phones or with PeerJS's public server (not reachable from the test environment).
